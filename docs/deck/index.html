The product

The unit of work is a case.
Not a document. Not a chat.

Four authorities. Each one does exactly one thing.

ModelInvestigates

Reads records, finds amendments, drafts the smallest request per blocker.

CodeProves

Decimal checks, tolerances, receipt allocation. Only rules clear a blocker.

HumanSends

Approves recipient and message. Owns the money decision.

ERPPays

Receives the packet in its existing approval flow. Resolve has no payment permission.

Architecture

Let the model investigate.
Keep the money logic in code.

1SourcesASP / ERP invoice, PO, receipts, amendments, case mailbox. No LLM in parsing.
→
2EvidenceImmutable records: source id, entity, version, hash, trust level.
→
3RulesDecimal arithmetic, tolerances, per-line receipt allocation.
↔
4Agent6 typed, case-scoped tools. 10-call budget. Proposes; never clears.
→
5PolicyRejects unknown sources, wrong owners, pay / bank language.
→
6ReviewerBlockers, drafts, packet → existing ERP approval.
Stack

Python / FastAPI · PostgreSQL · React · one structured-output model. No fine-tuning, no vector DB, no payment agent.

Controls that survive a bad document

Documents and email are untrusted input. No tool to send, pay or change bank details exists. Injection is a permissions problem, not a prompt problem.
